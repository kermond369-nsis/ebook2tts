## 复核原文

1. **复核结论**
有条件通过（须修复下列 MUST 级别硬伤，并补齐红线遗漏清查项后，升版 v0.2 定稿）。

2. **必须改 MUST**
- **MUST-1：多进程 LeakCanary 监控盲区**。
  - **为什么是硬伤**：本项目核心运行在 `:tts_service` 独立进程。LeakCanary 默认只能在 `Application` 的主进程中初始化并抓取泄漏。若不加特殊配置，引擎进程的 OOM 和泄漏将被彻底漏报，带来虚假的安全感。
  - **具体改法**：在 §二 方法与工具选型的 LeakCanary 行补充说明：“需专门配置以支持多进程（或显式在 `:tts_service` 进程初始化并导出 hprof）”。
- **MUST-2：NFR 性能指标采集项缺失**。
  - **为什么是硬伤**：《需求书》§5.1 的性能预算强制要求了“功耗（≤8%/h）”与“峰值内存（≤400MB）”，但计划 §6.2 的采集指标表格中直接漏掉了这两项。没有数据无法做合规判定。
  - **具体改法**：§6.2 增加功耗采集（建议通过 `dumpsys batterystats` 或 Battery Historian），并在内存指标中明确增加 Peak PSS 的记录要求（多次采样求 max）。
- **MUST-3：native 层缺陷审查工具空缺**。
  - **为什么是硬伤**：项目强依赖 SherpaONNX 和 JNI 接口，且《需求书》§5.2 明确点名了“AddressSanitizer 无确定性泄漏报告”。计划 §二 目前全系都是 JVM/Flutter 工具，无法探查 C++ 层的指针越界、UAF 或内存泄漏。
  - **具体改法**：在 §二 增加 AddressSanitizer (ASan) 或 HWASan（Android NDK 支持），专门针对 native 层的泄漏与越界访问。
- **MUST-4：防呆红线清查未完全落地到矩阵**。
  - **为什么是硬伤**：计划 §八 要求遵守“九条红线”，但在 §四 的缺陷清查矩阵中，漏掉了对红线 5、6、7、9 的具体动作，导致“全方位清查”出现致命盲区（见下方核验表）。
  - **具体改法**：将这四条红线对应的实质性检查点（native锁内释放、淡化边界、严禁IO、SAF安全提取）作为独立子项补进 §四 的表格中。

3. **建议改 SHOULD**
- **SHOULD-1：CI 配置污染主仓风险**。如果在审计仓使用平行仓库方案（方案 A），审计专用的 GitHub Actions workflows（可能含独有环境变量或分析插件）在合入主仓时容易引发冲突或密钥报错。建议在 §三 的“合并闸门”增加卡点：“合入主仓 PR 需剔除或隔离仅属于审计仓的专属 CI 配置文件”。
- **SHOULD-2：极端弱网下的在线 TTFT 退化验证**。在 §四 “engine 在线链路”中，应补充“DNS 黑洞 / 极端延迟下的回落表现”，验证底层请求超时设置是否能防住长时间无声。

4. **可选 MAY**
- **MAY-1**：在 §6.2 性能打点的原始日志中，建议记录设备当时的 CPU 温度状态（Thermal throttling state）。模拟器或无散热真机长期长跑易降频，补充环境量能防止 A/B 相对性能对比被温度误导。

7. **我无法确认/需实查的点**
- **甲方真机供给情况**：无法核实甲方是否能满足 DQ-P7-2 提供 ARM 真机，如果无法提供，因指令集与 NEON 优化差异，模拟器上的 RTF 及功耗表现对于实际终端设备毫无参考价值。
- **Android 系统后台服务强杀真实策略**：当前计划严重依赖 Android FGS (前台服务) 做下载，以及独立进程服务做推理。Android 14+ / 15 对后台拉起 FGS 及超时有严格限制，模拟器无法 100% 反映不同厂商魔改 ROM 下的真实冻结行为，需在国产真机实查。
- **在线模型并发限流**：MiMo 等上游 API 的免费额度策略、Token 限流机制及网络出口质量会大幅扰动首包 TTFT 测量的有效性，单次实测不足以作为基线承诺。
