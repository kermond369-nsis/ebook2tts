## 一、实施线对 agy 修正意见的核验（**已独立复核，采纳**）

agy 指出：**不能直接把 `READY_WAIT_MS` 拉长**，因为"`requestStop()` 只更新了 `stopAtMs`，没有调用 `signalReady()` 唤醒条件变量"，否则中止会挂起到超时。

**实施线源码核验（`SynthesisCoordinator.kt`，分支 `p7/audit` = `3b257e2`）**：

| 行号 | 事实 |
|---|---|
| 124–126 | `fun requestStop() { stopAtMs = SystemClock.uptimeMillis() }` —— **仅置标志，无任何唤醒动作** |
| 175–176 | `private fun signalReady() { readyLock.withLock { readyCond.signalAll() } }` —— **唤醒能力已存在但未被 stop 路径调用** |
| 233 | `signalReady()` 的唯一调用点＝**重载完成**路径（`reload ok`） |
| 733–746 | `awaitBackend()` 在 `readyLock` 内 `readyCond.await(remain)` 循环等待；每轮检查 `isStopped()` 与状态 |

⇒ **agy 的修正成立**：等待线程只能被"就绪信号"或"超时"唤醒；客户端中止**不会**立即唤醒它。故——

- **现状影响**：在冷加载窗口内取消朗读时，**中止响应最坏延迟 ≈ 剩余等待预算（≤1500 ms）**；
- **若按原方案①直接提高预算到 5000 ms**：该延迟会**恶化到 ≈5 s**，与"客户端中止须立即静默退出"的 AOSP 契约背离（也违背"取消即时生效"的既定工程口径，参见 P6 对下载取消的同类要求）。
- ⇒ **修复顺序必须调整**：**先**让 stop 路径唤醒等待者，**再**提高预算。已据此改写台账 F-009，并新增 **BUG-P7-013**。

## 三、复核原文

**A. 根因假设验证**
**成立**。
**依据**：
1. **时间线完全吻合**：日志显示客户端 00:54:40.184 发起请求，引擎 00:54:41.698 拒绝请求并抛出 `backend_not_ready`，差值 `1.514s`，精准对应 `SynthesisCoordinator.kt` 第 58 行的 `READY_WAIT_MS = 1500L` 超时预算。
2. **源码逻辑印证**：`awaitBackend()` 中的 `readyCond.await(remain)` 在超时后会返回 `null`，外层判断 `engine == null` 且非中止、非模型缺失状态下，对应的 reason 兜底分支正好是 `"backend_not_ready"`。
3. **不存在其它干扰路径**：能让 `awaitBackend()` 提前返回 `null` 的只有 `isStopped()`（中止，日志会打 `reason=stopped`）或 `sm.state` 异常（日志会打 `no_model` / `engine_error`），均与实测日志排他，证明**仅有超时**这一条发生路径。

**B. 修复建议的副作用与第三条路**
- **建议①（提高预算）的红线风险**：有**严重的违反 AOSP 契约风险**。源码第 124 行 `requestStop()` 仅更新了 `stopAtMs` 标志，**并没有调用 `signalReady()` 唤醒条件变量**。若盲目把等待预算提高到 5000ms，一旦客户端在加载期发起中止，合成线程会死等直到加载完成或 5s 超时，期间彻底挂起，直接违反“客户端中止须立即静默退出”的系统要求。
- **建议②（异步预热）的局限**：属正面优化，无明确风险。但在低端设备或极端系统调度下，依然可能存在耗时大于 1.5s 的情况，治标不治本。
- **更稳妥的第三条路（推荐）**：先在 `requestStop()` 函数中补充 `signalReady()` 调用，以确保收到中止指令时能立即中断 `awaitBackend()` 的等待并退出；然后再安全地将 `READY_WAIT_MS` 提高至足够大（如 5000ms 或更长），彻底解决加载竞态。

**C. 缺陷分级研判**
**定级 P1 合理，不建议降级**。
**理由**：根据日志 00:54:42.561 `onStart nowSpeak:26` 可知，首句（25）失败后 Legado 自身直接跳到了下一句继续朗读，引擎确实没有崩溃且成功恢复。但从有声书体验而言，每次冷启动都会**稳定漏读第一句话**（确定性的音频内容丢失），严重破坏了 AR-§4.8 连续性红线，且用户除了手动倒退无任何规避手段。这种直接影响核心功能的确定性缺失属于 P1 范畴。

**D. BUG-P7-010 推断复核**
**成立**。
**依据**：AOSP `TextToSpeech.java` 确有注释表明标准路由是 `System connection`（UID 1000 发起）。UID 1000 绑定组件时天然免疫权限校验。但如果不加替代控制，直接删掉不存在的 `BIND_TTS_SERVICE`，`LocalTextToSpeechService` 将变成一个完全裸露的导出组件（`exported=true`）。任何第三方恶意 App 都可以绕过系统管理直接发起 `bindService`，盗用本引擎进行后台无限量静默合成（甚至白嫖在线 MiMo 额度）。保留权限拦截机制是必须的。

**总结**
BUG-P7-011 根因确为 1.5s 等待不足，但直接拉长超时会因 `requestStop` 漏唤醒而导致中止挂起；BUG-P7-010 的防裸奔推断正确，台账分析整体极其精准。
