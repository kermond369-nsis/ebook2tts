## 二、方法总则（成熟项目优先，禁自造轮子）

**铁律落地**：清查与调优一律使用成熟、社区验证过的工具与官方 API；**禁止**自写"等效"检测/基准框架；**禁止**独立自证闭环——由 **agy 逐批次独立复核**（只读、可驳回）。

## 三、仓库与分支流程（**待甲方裁决 DQ-P7-1**）

### 3.1 事实（已核实，2026-09-16）

- 主仓 `kermond369-nsis/ebook2tts-local`（public，owner = 当前账号本人）；
- **GitHub 不允许把仓库 fork 到拥有它的同一账号**，故**无法**用"Fork 按钮"得到同账号的 fork；该账号名下**没有** Organization。

### 3.2 方案选择（**2026-09-16 甲方二次裁定后定案**）

甲方口径澄清：「两个名字不一致的仓库——**一个是公开、在测试的是私密**；测试完成后把改动合并到主仓库」，选择权交实施线。

**最终选择＝方案 A'（新建 private 平行仓）**，与既有方案 A 的差别仅在**私密**与**命名**：

| 项 | 定案值 |
|---|---|
| 公开主仓（发布用） | `kermond369-nsis/ebook2tts-local`（**public**，工作期间 `main` 零改动、零推送） |
| 私密测试仓（工作用） | **`kermond369-nsis/ebook2tts-local-p7`（private，新建）** —— 与主仓**名字不一致**、内容含全部改动与 `audit/` 文档目录 |
| 工作分支 | `p7/audit`（本地与私密仓同名） |
| 合并闸门 | 私密仓全绿 + agy 复核 + 甲方确认 → 同一批提交推送至**主仓**分支 `p7/landing` → 主仓开 PR → 甲方确认合并 → 主仓 `main` 更新、CI/Release 复绿核验 |
| 为何不用 GitHub fork | GitHub **不允许** fork 到拥有它的同一账号（已核实），该账号亦无 Organization；`s/公开主仓/私密测试仓` 的平行仓方案等价且零额外账号动作 |

> 依据：甲方 2026-09-16 二次澄清（"两个名字不一致的仓库…一个是公开，在测试的是私密…合并到主仓库"）。

### 3.3 合并闸门（三方案通用，唯一入口）

```
审计仓 提交（每次一个批次） 
  → ① 全绿：:core:test / :engine:testDebugUnitTest / flutter analyze+test / 审计仓 CI（含静态门）
  → ② agy 独立复核报告（含九条红线逐条核验表），无"必须改"未闭环项
  → ③ 甲方确认
  → ④ 推送同一批提交至主仓分支 p7/landing（git fetch 审计仓 + push 主仓）
  → ⑤ **改动白名单审查**：PR diff 仅允许 `core/` `engine/` `app/` 源码与测试、`docs`（非公开约束类不入库）与必要文档；**禁止**携带审计仓专属 CI（`.github/workflows` 审计 job）、detekt/lint 配置、任何 secrets、代理配置、依赖清单变更（如确需改依赖须单列理由并经甲方逐条批准）
  → ⑥ 主仓开 PR（main ← p7/landing），甲方点合并（或甲方授权实施线合并）
  → ⑦ 合并后主仓 CI/Release 复绿核验，短 SHA 回填台账
```

**红线**：未过 ①②③ 一律不得出现在主仓任何分支上；审计仓的 CI 密钥/代理配置不得写入主仓。

## 六、性能协议（先量后治，禁主观描述）

### 6.1 环境与限制（**须甲方知晓，DQ-P7-2**）

- 现有调试目标：**MuMu 模拟器 x86_64 / Android 15**（`[LAN-WIN-HOST]:7555`），**无 ARM 真机**；
- 依 AR-§1.6「模拟器只做粗筛」，故：
  - 模拟器数据**只用于相对 A/B 与趋势**（同机同条件、前后对照）；
  - 《需求书》§5.1 的**绝对预算**（TTFT ≤500ms、RTF ≤0.5、PSS ≤220MB、双 ABI 包体 ≤60MB、功耗 ≤8%/h）**本轮无法在模拟器上完成判定**，需甲方提供 ARM 真机，或甲方裁决接受"基线 + 相对改进"口径；
  - x86_64 无法覆盖 `arm64-v8a/armeabi-v7a` 原生库性能特性（含 NEON 路径），结论须显式标注适用边界。

### 6.2 指标与采集（复用既有打点，不新增私有框架）

| 指标 | 采集方式 | 样本规则 |
|---|---|---|
| 引擎冷启/就绪 | `am start -W`（TotalTime/WaitTime）＋ 徽标 `INIT→CREATED→READY` 打点 | 冷启 ×5 取中位数，报 P50/P95 |
| 首包 TTFT（本地/在线） | 既有 `PERF|ttfb_ms` 打点 | 同文本 ×10，报中位数与分布 |
| RTF / total_ms / drop | 既有 `PERF|req=…` 打点 | 同文本 ×10 |
| 内存 | `dumpsys meminfo` PSS（总/Java/**Native**）＋ **Peak PSS（多次采样取 max）** ＋ Perfetto heap profile | 基线点 + 长跑每 10min |
| **功耗** | `dumpsys batterystats`（复位后按 NFR §5.1 标准条件：灭屏、飞行模式、耳机 50% 音量、1h 连续朗读）＋ `dumpsys battery` 电量曲线 | 每次 ×1，记录起止电量与时长 |
| **环境量（防误判）** | SoC/电池温度与热状态（`dumpsys thermalservice`、`/sys/class/thermal/*`）、热降频标记 | 每次测量随记，用于剔除热降频导致的漂移 |
| 卡顿/帧 | `dumpsys gfxinfo framestats` ＋ Perfetto | 滚动/翻页场景 ×3 |
| 下载吞吐与选源质量 | 既有 `probe|…`/`picked|…`/`GET|code=206` 打点 | 每源 ×3，记录时间与出口 |
| 包体 | `apkanalyzer`/`ls -l` APK + 各 ABI 拆分体积 | 每次构建 |
| 崩溃/ANR | `logcat`（`FATAL|SIGABRT|ANR in`）＋ `dumpsys dropbox` | 全批次全程 |

**采集纪律**：每次测量记录（提交 SHA / 设备 / ABI / 模型 / 文本 / 网络出口 / 时间），原始输出落盘，**禁止**只留结论数字；异常值弃用需给规则（如首轮预热不计入）。

### 6.3 已知调优候选（来自 P6 实测，非推断）

| # | 候选 | 现状证据 |
|---|---|---|
| T1 | **首包 TTFT**（本地 0.6~4s） | `total_ms ≈ 音频时长 + ttfb` ⇒ 瓶颈在首包与实时推流节拍，非推理吞吐 |
| T2 | **镜像测速质量** | 64KB Range 探测严重低估（探得 ~20KB/s，实下 ~2MB/s 级）⇒ 选源可能次优 |

| T4 | **线程与模型档位** | 线程自适应已落地（模拟器 RTF 1.60→1.37~1.42）；档位/量化与核数组合未系统扫描 |
